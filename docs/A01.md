# A01 — Browser-Audit einer JS-Site

Diese Aufgabe gibt einem KI-Modell einen echten Chrome in die Hand und lässt es
eine kleine Website prüfen. Sie ist die komplizierteste Aufgabe des Benchmarks,
und sie ist die einzige, bei der man selbst mitspielen kann: Die Prüflandschaft
lässt sich lokal starten und mit den eigenen Werkzeugen untersuchen — Browser,
Screaming Frog, curl.

**Stand:** Aufgabenversion 1 · 26 Adressen · 22 Fehlertypen · 31 Befunde ·
4 Kontrollseiten ohne Befund · 14 Fehlalarm-Fallen

Dieses Dokument ist für Menschen, die die Aufgabe nachvollziehen oder selbst
lösen wollen. Warum die Aufgabe so gebaut ist, wie sie gebaut ist, steht in
`tasks/a01_browser_audit.md`.

> **Achtung, Spoiler.** Ab dem Abschnitt „Die Auflösung" stehen alle Befunde
> im Klartext. Wer sich selbst daran versuchen will, hört davor auf zu lesen.

---

## 1. Worum es geht

Ein Online-Shop für Wandkarten („Kartenshop") rankt schlecht und wirkt im
Betrieb träge. Die Website hat 31 technische Fehler, verteilt über 26 Adressen.
Manche sieht man im Quelltext, manche erst im gerenderten DOM, manche nur im
Netzwerkprotokoll — und einige nur, wenn man die Seite ein zweites Mal aufruft
oder sich als Googlebot ausgibt.

Dazu kommen vier Seiten, die **keinen** Fehler haben, und vierzehn Stellen, die
wie ein Fehler aussehen und keiner sind. Wer pauschal meldet, verliert genauso
wie wer nichts findet.

Das Ergebnis ist eine Liste von Paaren aus Seite und Fehler-Id:

```json
[{"page": "home.html", "issue": "content_requires_js"}, …]
```

## 2. Die Prüflandschaft selbst starten

### Voraussetzungen

**Docker.** Die Prüflandschaft ist mehr als ein Ordner mit HTML-Dateien: Sechs
der 26 Adressen haben gar keine Datei, und was dort ausgeliefert wird,
entscheidet eine nginx-Konfiguration. Ein einfacher Dateiserver zeigte dort sechs
404er, und fünf Befunde fehlten — also eine andere Website als die, die gemessen
wird.

**uv.** Das Projekt läuft über [uv](https://docs.astral.sh/uv/).

### Starten

```bash
cd german_seo_bench
uv run python -m german_seo_bench.testsite
```

Der Befehl prüft vorher, ob der Port benutzbar ist, startet denselben nginx mit
derselben Konfiguration wie im Messlauf und meldet danach, ob die Site
antwortet:

```
Prüflandschaft:  http://www.example.net/
ersatzweise:     http://127.0.0.1/

Damit der Name auflöst, muss diese Zeile in /etc/hosts stehen:
    127.0.0.1	www.example.net

Beenden mit Strg-C.

  ✓ Die Prüflandschaft antwortet: http://www.example.net/home.html
```

Beenden mit **Strg-C**; der Container wird dabei aufgeräumt.

### Warum `www.example.net`

Die geprüfte Website liegt unter `www.example.net`, und drei Canonical-Links
zeigen nach `example.com`. Beide Domains sind nach **RFC 2606** für genau
solche Zwecke reserviert und lösen nirgends auf einen echten Host auf. Zwei
verschiedene davon bilden den Unterschied ab, um den es bei den
Canonical-Befunden geht: **eigene Site** gegen **fremde Domain**.

Damit der Name auf den eigenen Rechner zeigt, braucht es einen Eintrag in der
hosts-Datei (unten je Betriebssystem). Ohne ihn geht es auch — dann über
`http://127.0.0.1/`, aber `sitemap.xml` und die Canonicals nennen absolute
Adressen, und ein Crawler folgt ihnen dann ins Leere.

> **Wenn der Browser „nicht erreichbar" sagt, obwohl der Server läuft:** Die
> Adresse **mit `http://`** eingeben. Chrome versucht bei einer Adresse ohne
> Schema zuerst `https://`, und die Prüflandschaft spricht nur HTTP.

## 3. Einrichtung je Betriebssystem

Zwei Dinge sind einzurichten: der **hosts-Eintrag**, damit der Name auflöst, und
**Port 80**, damit die Adressen ohne Portangabe stimmen.

### Linux

**hosts-Eintrag:**

```bash
echo "127.0.0.1 www.example.net" | sudo tee -a /etc/hosts
```

**Port 80.** Läuft Docker als root-Dienst (klassische Installation), ist nichts
zu tun. Bei **rootless Docker oder Podman** — auf Fedora die Vorgabe —
veröffentlicht der Container seine Ports unter deinem Benutzerkonto, und Ports
unter 1024 sind privilegiert. Prüfen:

```bash
sysctl net.ipv4.ip_unprivileged_port_start    # 1024 = Ports darunter gesperrt
docker info | grep -i rootless
```

Freigeben:

```bash
sudo sysctl net.ipv4.ip_unprivileged_port_start=80          # bis zum Neustart
echo net.ipv4.ip_unprivileged_port_start=80 \
  | sudo tee /etc/sysctl.d/99-unprivileged-ports.conf       # dauerhaft
```

Das ist der Fall, der am meisten Zeit kostet, wenn man ihn nicht kennt:
`docker compose up` meldet den Fehlschlag zwar, **läuft aber weiter**. Der
Container steht, nginx horcht darin auf Port 80 — nur nach außen kommt nichts
durch. Der Browser sagt „nicht erreichbar", `curl` sagt `Could not connect`,
und keine der beiden Meldungen nennt die Ursache. Deshalb prüft
`german_seo_bench.testsite` das vorab.

### macOS

**hosts-Eintrag:**

```bash
echo "127.0.0.1 www.example.net" | sudo tee -a /etc/hosts
sudo dscacheutil -flushcache; sudo killall -HUP mDNSResponder
```

**Port 80.** Docker Desktop darf ihn veröffentlichen, dafür ist nichts
einzurichten. Klemmt es trotzdem, hält ihn ein anderer Dienst:

```bash
sudo lsof -nP -iTCP:80 -sTCP:LISTEN
```

Typische Kandidaten sind ein eingeschalteter Apache (`sudo apachectl stop`) oder
ein zweiter Container.

> **Warum nicht `.local`?** Diese Pseudo-TLD gehört unter macOS dem
> mDNS-Dienst (Bonjour). Ein hosts-Eintrag darunter führt zu schwer
> durchschaubaren Auflösungsproblemen — `example.net` hat dieses Problem nicht.

### Windows

**hosts-Eintrag.** Die Datei liegt unter

```
C:\Windows\System32\drivers\etc\hosts
```

Sie lässt sich nur mit Administratorrechten ändern: Editor per Rechtsklick „Als
Administrator ausführen" starten, die Datei dort öffnen, die Zeile anhängen,
speichern. Danach:

```powershell
ipconfig /flushdns
```

In PowerShell als Administrator geht es auch in einer Zeile:

```powershell
Add-Content -Path $env:SystemRoot\System32\drivers\etc\hosts -Value "`n127.0.0.1 www.example.net"
ipconfig /flushdns
```

**Port 80.** Docker Desktop veröffentlicht ihn normalerweise ohne Weiteres. Zwei
Dinge halten ihn unter Windows häufig besetzt:

```powershell
netstat -ano | findstr :80            # welcher Prozess horcht?
tasklist /fi "pid eq <PID>"
```

- **IIS** bzw. der Dienst *World Wide Web Publishing Service* (`W3SVC`) —
  anhalten über „Dienste" oder `Stop-Service W3SVC`.
- **Reservierte Portbereiche** von WinNAT/Hyper-V. Nachsehen mit:

  ```powershell
  netsh interface ipv4 show excludedportrange protocol=tcp
  ```

  Liegt 80 in einem reservierten Bereich, hilft ein Neustart des
  Host-Netzwerkdienstes (`net stop winnat` / `net start winnat`) oder ein
  anderer Port.

### Wenn Port 80 nicht geht: die Ausweichlösung

```bash
uv run python -m german_seo_bench.testsite --port 8099
```

Dann läuft die Site unter `http://www.example.net:8099/` bzw.
`http://127.0.0.1:8099/`.

> **Der Preis:** `sitemap.xml`, `robots.txt` und die Canonical-Links nennen
> absolute Adressen **ohne Port** (`http://www.example.net/…`). Ein Crawler, der
> der Sitemap folgt, landet damit auf Port 80 und findet nichts. Zum
> Durchklicken im Browser reicht der hohe Port; für einen Screaming-Frog-Crawl
> über die Sitemap nicht. Von der Start-URL aus crawlen geht dagegen normal.

### Prüfen, ob es läuft

```bash
curl -I http://127.0.0.1/home.html        # Server erreichbar?
curl -I http://www.example.net/home.html  # Name löst auf?
```

Antwortet das erste nicht, liegt es am Server (meist Port 80, siehe oben).
Antwortet das erste und das zweite nicht, liegt es am hosts-Eintrag. Antworten
beide und nur der Browser nicht, ist es die HTTPS-Erhöhung.

## 4. Die Aufgabe, wie ein Modell sie bekommt

Das Modell bekommt **kein HTML in den Prompt**. Es bekommt die Liste der
Adressen, einen geschlossenen Fehlerkatalog und den Auftrag, mit den
Browser-Werkzeugen zu prüfen. Sinngemäß:

> Diese kleine Website rankt schlecht und wirkt im Betrieb träge. Prüfe jede der
> folgenden Seiten mit den Browser-Werkzeugen auf technische SEO- und
> Performance-Fehler. Beurteile nicht den HTML-Quelltext allein, sondern das,
> was der Browser daraus macht — das DOM nach dem Ausführen von JavaScript, die
> Netzwerk-Requests samt nachgeladener Ressourcen, Weiterleitungen, die
> Stabilität des Layouts nach dem Laden und das Verhalten bei Interaktion. Ein
> Teil der Fehler zeigt sich erst, wenn du eine Seite scrollst oder ein
> Bedienelement anklickst. Beurteile im Desktop-Viewport **1280 × 900** Pixel.

Der Viewport ist keine Nebensache: Ob ein Bild im ersten sichtbaren Bereich
liegt und wie stark sich das Layout verschiebt, hängt an der Fenstergröße.

## 5. Wie die Prüflandschaft aufgebaut ist

```
german-seo-bench/src/german_seo_bench/data/a01_browser_audit/
├── site/                     die ausgelieferten Dateien
│   ├── *.html                die Seiten
│   ├── style.css, layout.css zwei Stylesheets — die Trennung ist Absicht
│   ├── app.js, ui.js, tracker.js
│   ├── hero.svg, foto.svg
│   ├── sitemap.xml, robots.txt
├── testsite.nginx.conf       die Auslieferungsregeln — der halbe Benchmark
├── compose.yaml              Messlauf: Agent + Prüflandschaft, Netz `internal`
├── local.compose.yaml        lokaler Server (dieses Dokument)
└── reference.compose.yaml    Referenz-Erzeugung
```

### Vier Adressen ohne Datei

Unter `preise.html`, `schulen.html`, `tipps.html` und `archiv.html` liegt
**keine Datei**. Was dort ausgeliefert wird, entscheidet allein die
nginx-Konfiguration — und die bekommt kein Modell zu sehen. Dazu kommen
`umzug.html` und `shop.html`, die weiterleiten.

Das ist der Grund, warum der lokale Server denselben nginx fährt: Ohne ihn
sähest du an sechs von 26 Adressen etwas anderes als das Modell.

### Die nginx-Konfiguration

Drei `map`-Blöcke setzen Variablen aus der Anfrage, fünf `location`-Blöcke
nutzen sie:

```nginx
map $cookie_besuch  $wiederkehrer { default "-first";    "~." "-again"; }
map $cookie_archiv  $archivstand  { default "-first";    "~." "-again"; }
map $http_user_agent $variant     { default "-visitor";
                                    "~*googlebot|bingbot|adsbot" "-bot"; }
```

**Auslieferung nach Kennung** — der SEO-Klassiker Cloaking:

```nginx
location = /preise.html {
    add_header Cache-Control "max-age=7200" always;
    try_files /preise$variant.html =404;
}
location = /schulen.html {
    add_header Cache-Control "no-store" always;
    try_files /schulen$variant.html =404;
}
```

Je nach User-Agent wird `preise-visitor.html` oder `preise-bot.html`
ausgeliefert. Die beiden Adressen unterscheiden sich in **einem** Detail, und
das ist Absicht: `preise.html` ist cachebar (`max-age=7200`) und sendet **kein**
`Vary: User-Agent`, `schulen.html` ist es nicht (`no-store`). Wer erst als
Besucher und dann als Crawler fragt, bekommt auf `preise.html` aus dem eigenen
Browser-Cache noch einmal die Besucher-Fassung — die zweite Anfrage erreicht den
Server nie. Auf `schulen.html` passiert das nicht. Die beiden Items trennen
damit zwei Fähigkeiten: „wechselt die Kennung überhaupt" und „umgeht dabei den
eigenen Cache".

**Auslieferung nach Besuchszahl** — sitzungsabhängiges noindex:

```nginx
location = /tipps.html {
    add_header Set-Cookie "besuch=1; Path=/; Max-Age=7200" always;
    add_header Cache-Control "no-store" always;
    try_files /tipps$wiederkehrer.html =404;
}
location = /archiv.html {
    add_header Set-Cookie "archiv=1; Path=/; Max-Age=7200" always;
    add_header Cache-Control "no-store" always;
    try_files /archiv$archivstand.html =404;
}
```

Beim ersten Abruf setzt der Server ein Cookie und liefert die indexierbare
Fassung; beim zweiten steht ein `noindex` im Kopf. Wer jede Adresse genau einmal
ansieht, sieht davon nichts. **Die Cookie-Namen sind verschieden** — mit
demselben Namen schaltete der Besuch der einen Adresse die andere mit um, und
der Befund hinge an der Abrufreihenfolge statt an der Auslieferung.

`no-store` ist hier Pflicht und damit genau umgekehrt zur gecloakten Seite: Dort
*ist* der Cache die Falle, hier würde er die Bedingung ersetzen.

**Weiterleitungen:**

```nginx
location = /umzug.html          { return 301 /umzug-zwischen.html; }
location = /umzug-zwischen.html { return 301 /kategorie.html; }
location = /shop.html           { return 301 /home.html; }
```

Zwei Sprünge sind eine Kette und ein Befund. **Ein** Sprung auf eine Seite mit
200 ist eine korrekte Weiterleitung und ausdrücklich **kein** Befund.

**Und eine Regel, die gar nichts tut:**

```nginx
location = /galerie.html {
    add_header Set-Cookie "ansicht=raster; Path=/; Max-Age=7200" always;
    try_files /galerie.html =404;
}
```

Hier wird ein Cookie gesetzt — und trotzdem immer dieselbe Datei ausgeliefert.
Mehr dazu im nächsten Abschnitt.

## 6. Die Fallen

Vierzehn Stellen sehen aus wie ein Befund und sind keiner. Zwölf davon liegen auf
Seiten, die **auch echte Befunde tragen** — eine Falle auf einer sonst sauberen
Seite bestraft nur den, der die Seite überhaupt ansieht.

Die Fallen in Gruppen, ohne zu verraten, wo welcher echte Befund liegt:

**Zahlen knapp unter der Schwelle.** Zwei Fallen liegen so, dass die Schwelle
rechnerisch nicht erreichbar ist — nicht bloß gemessen knapp darunter. Eine
Layout-Verschiebung, die sichtbar ist und unter CLS 0,1 bleibt; ein
Klick-Handler, der spürbar hängt und unter 200 ms bleibt.

**Richtig eingesetzte Technik.** Ein `loading="lazy"` unterhalb des ersten
Viewports ist korrekt und kein Befund. Ein `noindex` zusammen mit einem
Selbst-Canonical ist eine bewusste Entscheidung und kein Fehler. Eine einzelne
301 auf eine Seite mit 200 ist, wie eine Weiterleitung aussehen soll.

**Toter Code.** Fünf Seiten enthalten Codepfade, die im Quelltext genau wie ein
Befund aussehen und zur Laufzeit nichts tun — ein `location.replace()` hinter
einer Bedingung, die nie wahr wird; ein `document.title =` hinter
`matchMedia('print')`; ein Bildpfad, der 404 liefern würde, über einer leeren
Knotenliste; ein `noindex` hinter einem Query-Parameter, den keine Adresse
trägt; ein Skript-Nachladen hinter einem Schalter, der aus ist. Wer das
gerenderte DOM und das Netzwerkprotokoll ansieht, meldet nichts. Wer den
Quelltext nach Mustern durchsucht, sammelt fünf Falschmeldungen.

**Ein Hinweis ist kein Beleg.** Eine Adresse setzt ein Cookie und liefert
trotzdem immer dieselbe Datei aus. Wer aus „hier kommt ein `Set-Cookie`" auf
„sitzungsabhängige Auslieferung" schließt, ohne die zweite Antwort mit der
ersten zu vergleichen, meldet falsch.

**Zwillinge.** Zwei Seiten tragen dieselbe CSS-Klasse am selben Element — auf
einer ist der Textblock unsichtbar, auf der anderen nicht. Entschieden wird das
von einer Kaskade über zwei Stylesheets und eine Media Query, die beim
Messviewport greift. Nur `getComputedStyle` unterscheidet sie sicher.

**Attribute lügen.** Auf einer Seite stehen zwei große Bilder. Welches der
LCP-Kandidat ist, entscheidet die **per CSS gerenderte** Größe und nicht das
`width`-Attribut — und die beiden sind absichtlich vertauscht.

## 7. Wie gewertet wird

Nicht alle Fehler sind gleich schwer zu finden. Jeder Fehlertyp trägt deshalb
eine **Fähigkeitsklasse**: die billigste bekannte Strategie, die ihn holt.

| Klasse | genügt zum Finden | Befunde |
|---|---|---|
| `source` | die ausgelieferten Bytes lesen (HTML, JS, CSS, sitemap.xml) | 18 |
| `network` | die Antwortdaten statt des Rumpfs (Status, Weiterleitungskette) | 5 |
| `render` | gerendertes DOM, Geometrie, berechneter Stil | 4 |
| `request` | eine Anfrage unter besonderer Bedingung (Kennung, Cache-Umgehung) | 2 |
| `second_load` | Zustand über zwei Ladevorgänge hinweg | 2 |

**Der Score ist das F1 je Klasse, gemittelt über die Klassen** — nicht über alle
Befunde. Das macht einen großen Unterschied: 18 der 31 Befunde sind aus den
ausgelieferten Bytes entscheidbar. Mittelte man über die Paare, wögen diese 18
fast 60 % und ein reiner Quelltextleser käme auf 0,735. Über die Klassen
gemittelt kommt er auf **0,200**.

```
Löser                                        Score   (zum Vergleich: über Paare)
alles korrekt                                1.000     1.000
alle Klassen außer request und second_load   0.600     0.931
nur source                                   0.200     0.735
alles melden (jede Seite × jeder Fehlertyp)  0.120     0.103
```

Falschmeldungen zählen gegen die Klasse des gemeldeten Fehlertyps — sonst wäre
der Score ein reines Recall-Maß, in dem „alles melden" eine Eins bekäme.

## 8. Wie groß muss das Kontextfenster sein?

Die wichtigste Hardware-Frage für diese Aufgabe. Ein Agent schickt bei jedem
Zug das ganze bisherige Gespräch mit, und ein Browser-Snapshot einer Seite
kostet mehrere tausend Tokens. In Testläufen lag der **Median** der
Promptlänge einer Sitzung bei 30 000 bis 53 000 Tokens, die Spitzen reichten
bis knapp 88 000.

| Fenster | Urteil |
|---|---|
| **32k** | unbrauchbar — schon der **Median** einer Sitzung liegt darüber, nicht nur die Spitze |
| **64k** | Minimum; reicht für einen Teil der Läufe vollständig |
| **128k** | sicher |

Ein Modell mit 32k Fenster läuft typischerweise nach einigen Dutzend Aufrufen in
`exceed_context_size_error`. Wer so etwas als „Modell hat versagt" notiert, hat
die Größe eines Fensters gemessen und nicht ein Modell.

Das ist keine Eigenschaft des Modells, sondern der Aufgabe: 26 Adressen,
Snapshots als Werkzeugantworten. Wer die Zahl auf andere Audits überträgt,
rechnet mit der Zahl der Seiten und der Größe der Werkzeugantworten.

Der `local/`-Provider übersetzt die Überlauf-Meldungen
lokaler Server (llama.cpp meldet `exceed_context_size_error`, nicht OpenAIs
`context_length_exceeded`). Dadurch greift Inspects `truncation="auto"`: Der
Agent kürzt und macht weiter statt abzubrechen. Ein gekürzter Lauf hat
allerdings Teile seiner eigenen Beobachtungen vergessen und ist mit einem
ungekürzten nicht vergleichbar — zu erkennen an `stop_reason: model_length` in
den Modellereignissen des Logs.

## 9. Einen echten Lauf starten

```bash
cd german-seo-bench
uv run inspect eval german_seo_bench/a01_browser_audit \
  --model local/qwen3.8-27b --model-base-url http://192.168.1.50:8080/v1
```

Braucht Docker. Zwei Schalter sind interessant:

```bash
-T agent=goose      # statt Inspects eigenem Werkzeug-Loop ein Agent-CLI
-T report=false     # ohne den Kundenbericht am Ende (spart ~5 min je Lauf)
```

Nach dem Lauf liegt in `reports/` ein Kundenbericht als PDF — das Modell fasst
seine eigenen Befunde für einen Auftraggeber zusammen. Der geht **nicht** in die
Wertung ein.

Hinter der Zusammenfassung und vor den Befunden steht darin ein **rot
umrandeter Kasten**, den nicht das Modell geschrieben hat, sondern der
Benchmark:

```
Bewertung dieses Berichts durch den Benchmark
Von 6 gemeldeten Problemen gibt es 3 nicht; 28 tatsächlich vorhandene fehlen.
50% der Meldungen sind richtig · 10% der Probleme gefunden · Score 0,13 von 1,00
Frei erfunden: poster-a3.html/client_side_redirect, …
```

War der Lauf gestört, steht das weiß auf rot **über** den Zahlen — etwa „Das
Kontextfenster des Modells war 9× voll". Harte Abbrüche (Zeitgrenze,
Netzwerkfehler) stehen dort nicht: Sie beenden den Lauf, bevor der Bericht
entsteht, dann gibt es gar kein PDF.

Er ist der Grund, warum man dem PDF trauen kann: Ein Bericht aus einem Lauf mit
Score 0,13 liest sich genauso überzeugend wie einer mit 0,96 — gleiche
Gliederung, gleiche Sprache, gleiche Empfehlungen. Die Zeile „Frei erfunden"
sagt, welche Empfehlung auf nichts beruht.

Wiederholungen gehören über **verschiedene Aufrufe** verteilt, nicht in einen
Aufruf mit `--epochs`: Bei einer Agent-Aufgabe schwankt die gewählte
Arbeitsweise zwischen Aufrufen stärker als das Sampling innerhalb eines Aufrufs.

### Die beiden schwierigsten Items

**`hidden_by_css` auf `technik.html`.** Die Unsichtbarkeit steht in keiner
einzelnen Datei:

```
style.css    .rand { visibility: hidden }         Container ausgeblendet
             .rand > * { visibility: visible }    Kinder holen sie sich zurück
layout.css   @media (min-width: 68.75em)          greift bei 1280 px
               .rand > .einschub { visibility: inherit }
                                                  der Block erbt die Ausblendung
zubehoer.html  <div class="rand offen">           dieselbe Klasse, sichtbar
```

Jede Zeile für sich ist harmlos. Unter 1100 Pixeln Fensterbreite ist der Block
auf **beiden** Seiten sichtbar — der Befund hängt am Messviewport.

**Der zweite `lazy_lcp_image` auf `zubehoer.html`.** Welches Bild der
LCP-Kandidat ist, entscheidet die gerenderte Größe:

| Bild | Attribute | per CSS gerendert | `loading` |
|---|---|---|---|
| `hero.svg` | 1200 × 600 | 220 × 110 (24 200 px²) | — |
| `foto.svg` | 300 × 200 | 900 × 600 (540 000 px²) | `lazy` |

Die Mindestfläche für einen LCP-Kandidaten liegt bei 40 000 px². Nach Attribut
ist das große Bild nicht lazy — eine Attribut-Heuristik findet nichts.

### Mehrfach vorkommende Befunde

`noindex_after_render`, `pagination_404`, `duplicate_title`, `broken_resource`,
`title_changed_by_js`, `content_requires_js`, `cloaked_content`,
`noindex_on_second_visit` und `lazy_lcp_image` kommen je **zweimal** vor. Wer je
Katalogeintrag nach dem ersten Treffer aufhört, verliert Recall.
